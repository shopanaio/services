# Must-have функциональность админки для управления поиском Shopana

## Назначение

Этот документ описывает обязательное поведение раздела управления обычным
текстовым поиском в Shopana Admin. Он определяет пользовательские возможности,
но не содержит плана реализации, API-контрактов, схемы хранения данных или
деталей поискового индекса.

Раздел предназначен для администратора магазина, который должен уметь:

- проверить, что увидит покупатель по конкретному запросу;
- исправить запросы с нерелевантными или пустыми результатами;
- связать разные названия одного товара через синонимы;
- поднять выбранные товары для конкретных запросов;
- управлять базовым поведением текстового поиска;
- оценить качество поиска по реальным действиям покупателей;
- видеть, готов ли поисковый индекс к работе.

Настройки применяются только к поиску внутри storefront Shopana. Они не влияют
на индексацию магазина внешними поисковыми системами.

## Структура раздела

В Shopana Admin должен быть единый раздел `Search`, содержащий следующие
обязательные страницы:

1. `Overview` — состояние поиска и ключевые показатели.
2. `Preview` — проверка реальных результатов поиска.
3. `Synonyms` — группы равнозначных слов и фраз.
4. `Product boosts` — продвижение товаров по конкретным запросам.
5. `Settings` — общее поведение поиска.
6. `Analytics` — запросы, результаты, клики и покупки.

## Overview

Главная страница поиска должна давать краткое представление о его состоянии без
необходимости открывать отдельные отчеты.

Администратор должен видеть:

- статус поискового индекса: `Ready`, `Updating`, `Failed`;
- дату и время последнего успешного обновления;
- количество проиндексированных товаров по сравнению с количеством товаров,
  которые должны быть доступны в storefront;
- число поисков за выбранный период;
- долю запросов без результатов;
- долю запросов с кликами;
- наиболее частые запросы без результатов;
- наиболее частые запросы с результатами, но без кликов.

Из запроса без результатов или без кликов администратор должен иметь возможность
сразу перейти в Preview, создать группу синонимов или создать product boost.

Если индекс обновляется, админка должна показывать состояние `Updating`.
Если индекс недоступен или последнее обновление завершилось ошибкой, админка
должна явно показывать проблему, а не отображать состояние `Ready`.

## Search Preview

Preview должен воспроизводить поведение storefront search и использовать те же
правила поиска, видимости, локали, доступности и ранжирования.

Администратор задает:

- поисковую фразу;
- локаль;
- при необходимости category или collection scope.

Preview показывает:

- итоговую нормализованную поисковую фразу;
- найденные товары в фактическом порядке выдачи;
- общее количество результатов;
- наличие товара;
- причину заметного изменения позиции, если применен synonym или product boost;
- применялся ли fuzzy fallback;
- состояние `No results`, если совпадений нет.

Preview не должен показывать технические SQL-выражения или внутренние значения
BM25 score обычному администратору. Диагностика должна быть выражена понятными
причинами: `Matched title`, `Matched synonym`, `Fuzzy fallback applied`,
`Product boost`.

Preview не показывает «исправленный запрос», потому что `pg_search` не исправляет
и не переписывает введенную фразу. Он только допускает совпадение токенов на
заданном расстоянии редактирования.

Из Preview можно открыть товар, создать boost для введенного запроса или начать
создание группы синонимов с уже заполненной поисковой фразой.

## Synonyms

Синонимы должны храниться группами равнозначных слов или фраз. Например,
`кроссовки`, `кеды` и `sneakers` могут входить в одну группу, если для данного
магазина они должны возвращать общий набор результатов.

Для каждой группы администратор задает:

- внутреннее название группы;
- локаль;
- два или более слова либо фразы;
- состояние `Active` или `Inactive`.

Внутреннее название помогает находить группу в админке и не участвует в поиске.
Активная группа расширяет запрос всеми значениями группы в обе стороны. Поиск по
любому значению должен находить товары, соответствующие другим значениям.

Поведение должно учитывать следующие правила:

- фраза из нескольких слов считается цельной поисковой фразой;
- одинаковое значение нельзя одновременно использовать в нескольких активных
  группах одной локали;
- пустые и дублирующиеся значения не сохраняются;
- изменение группы должно проверяться в Preview до или сразу после сохранения;
- группу можно временно отключить без удаления;
- синонимы не используются для точного поиска по SKU и barcode;
- обычные опечатки не должны добавляться как синонимы: их обрабатывает typo
  tolerance.

Список групп должен поддерживать поиск по названию и значениям, фильтр по локали
и состоянию, а также показывать дату последнего изменения.

## Product Boosts

Product boost повышает позицию выбранного товара, когда запрос покупателя
соответствует заданному слову или фразе. Boost не обязан делать товар абсолютным
первым результатом, но должен давать ему явный приоритет среди релевантных
результатов.

Для boost администратор задает:

- один или несколько товаров;
- одну или несколько точных поисковых фраз;
- локаль;
- состояние `Active` или `Inactive`.

Boost применяется только когда товар соответствует storefront-условиям
видимости. Скрытый, удаленный или недоступный для публикации товар не должен
появляться в выдаче только из-за boost.

Недоступный товар обрабатывается в соответствии с общей настройкой out-of-stock
products. Boost не должен обходить правило `Hide` и не должен поднимать
недоступный товар выше доступных при режиме `Place last`.

В списке boosts должны отображаться поисковые фразы, товары, локаль, состояние и
дата изменения. Администратор должен иметь возможность открыть Preview прямо из
boost и увидеть итоговую выдачу.

## Search Settings

### Searchable fields

Администратор должен видеть, какие свойства товара участвуют в текстовом поиске.
Для MVP должны поддерживаться как минимум:

- product title;
- variant title;
- SKU;
- barcode;
- vendor;
- product type или category name.

Title должен иметь наибольший приоритет по умолчанию. SKU и barcode должны
поддерживать точное и prefix-сопоставление и не расширяться синонимами или fuzzy
поиском.

Для каждого поддерживаемого поля администратор может включить или выключить его
участие в поиске. Поле product title отключить нельзя, чтобы магазин не мог
случайно остаться без базового поиска.

Если Shopana еще не индексирует конкретное поле, оно не должно отображаться как
активная рабочая настройка. Админка не должна позволять сохранить конфигурацию,
которую storefront фактически игнорирует.

### Typo tolerance

Typo tolerance в Shopana должна соответствовать fuzzy search, который
предоставляет ParadeDB `pg_search`. Это не spellcheck и не автоматическое
исправление текста запроса. `pg_search` разбивает запрос на токены и считает
токен совпавшим, если его Levenshtein distance до токена в индексе не превышает
заданное значение.

Расстояние учитывает посимвольные вставки, удаления и замены. `pg_search`
поддерживает edit distance только от `0` до `2`; `0` эквивалентно точному
совпадению токена. Поисковый движок не возвращает предполагаемое правильное
слово, поэтому storefront и Admin не должны обещать покупателю исправление в
форме «Возможно, вы имели в виду ...».

В must-have админка предоставляет один переключатель:

- `Off` — выполняется только обычный token match;
- `On` — если обычный поиск не вернул ни одного товара, Shopana повторяет поиск
  как fuzzy match с edit distance `1`.

Значение по умолчанию — `On`.

Обычный поиск всегда выполняется первым. Его результаты не смешиваются с fuzzy
результатами: fallback запускается только при нулевом результате. Благодаря
этому точные совпадения всегда сохраняют исходное BM25-ранжирование, а fuzzy не
расширяет уже успешную выдачу.

Fuzzy применяется к каждому токену текстового запроса. Для запроса из нескольких
слов сохраняется основная семантика Shopana: если обычный поиск требует
совпадения всех токенов, fuzzy fallback также требует совпадения всех токенов,
но допускает расстояние `1` для каждого из них.

В must-have не используется edit distance `2`. Хотя `pg_search` его
поддерживает, такой режим может возвращать слишком широкий набор результатов,
особенно для коротких слов и non-Latin текстов, включая кириллицу.

SKU и barcode никогда не проходят через fuzzy match: для них сохраняется точное
или prefix-сопоставление. Fuzzy также не применяется к запросу, который после
нормализации короче трех символов.

При использовании fuzzy storefront продолжает показывать исходный запрос без
автоматической замены текста. Admin Preview и Analytics отмечают только факт
`Fuzzy fallback applied`, но не показывают вымышленный «исправленный» вариант.

### Out-of-stock products

Для недоступных товаров администратор выбирает поведение в поисковой выдаче:

- `Show` — отображать в обычном порядке по релевантности;
- `Place last` — показывать после всех доступных совпадений;
- `Hide` — полностью исключать из результатов.

Значение по умолчанию — `Place last`. Правило применяется после текстового
сопоставления и имеет приоритет над product boosts.

### Locale behavior

Настройки поиска должны быть locale-aware. Синонимы, boosts и Preview всегда
работают в явно выбранной локали. Если настройка относится ко всем локалям, это
должно быть явно показано как `All locales`.

При отсутствии локализованного поискового документа Shopana не должна незаметно
смешивать результаты из другой локали. Такое состояние должно быть видно в
Preview как отсутствие локализованных данных.

## Search Analytics

Analytics должна показывать качество страницы результатов поиска.

Администратор выбирает период и локаль и видит:

- количество поисков;
- уникальные поисковые фразы;
- click-through rate результатов;
- purchase rate товаров, найденных через поиск;
- запросы по частоте;
- запросы без результатов;
- запросы с результатами, но без кликов;
- запросы, для которых применялся typo fallback;
- запросы, по которым покупатели часто переформулируют фразу.

Для каждой поисковой фразы должны отображаться как минимум:

- нормализованный текст запроса;
- локаль;
- количество поисков;
- среднее или последнее количество результатов;
- количество кликов;
- количество покупок;
- дата последнего поиска.

Из строки отчета администратор должен иметь возможность открыть запрос в Preview,
создать synonym group или product boost.

Для запросов без результатов должен существовать отдельный рабочий список. После
исправления администратор может отметить запрос как `Resolved` или `Ignored`, не
удаляя исторические данные аналитики.

## Index Status

Админка должна явно показывать состояние поисковых данных отдельно от состояния
каталога.

Обязательные данные:

- текущий статус индекса;
- время последнего успешного обновления;
- время последней попытки обновления;
- количество проиндексированных товаров по локалям;
- количество товаров, ожидающих обновления;
- понятное описание последней ошибки без внутренних stack trace.

Администратору доступно действие `Rebuild search index`. Перед запуском админка
предупреждает, что операция может занять время. Повторное нажатие во время
активного rebuild не запускает второй процесс, а показывает текущий прогресс.

После изменения synonyms, boosts или search settings интерфейс должен показывать
состояние применения изменений: `Pending`, `Applying`, `Applied` или `Failed`.
Настройка не должна выглядеть примененной, пока storefront использует старое
поведение.

## Общие требования к поведению

- Все изменения требуют явного сохранения.
- Несохраненные изменения должны быть заметны и защищены от случайной потери.
- Ошибки валидации показываются рядом с соответствующим полем.
- Успешное сохранение не означает успешное применение к индексу; эти состояния
  отображаются отдельно.
- Опасные действия, такие как удаление synonym group или rebuild индекса,
  требуют подтверждения.
- Настройки должны сохранять понятную историю последнего изменения: кто и когда
  изменил правило.
- Любую настройку, влияющую на выдачу, можно проверить через Preview.

## Что не входит в must-have

Следующие возможности не обязательны для первой версии Search Admin:

- semantic или vector search;
- персонализация выдачи по конкретному покупателю;
- ML-reranking;
- sponsored search и рекламные аукционы;
- визуальный поиск по изображению;
- сложные числовые коэффициенты ранжирования для администратора;
- ручное управление stemming и tokenizer;
- редактирование SQL, BM25 score или fuzzy distance;
- предложения «Возможно, вы имели в виду ...» без отдельного spellcheck-механизма;
- отдельное управление storefront-фасетами в Search Admin.

Фасеты, их значения, counts и variant-aware фильтрация остаются частью listing
contract Shopana. Search Admin управляет текстовым поиском и качеством его
результатов, но не дублирует интерфейс настройки фасетов.

## Основа требований

Поведение раздела опирается на возможности Shopify Search & Discovery:

- настройка типов результатов, product boosts, synonym groups и поведения
  out-of-stock products;
- отчеты по click rate, purchase rate, популярным запросам, запросам без
  результатов и запросам без кликов;
- связь аналитики с действиями по созданию synonyms и boosts.
