# Reviews Admin GraphQL SDL

## Scope

The schema under `src/api/graphql-admin/schema/` is an administrative contract.
It deliberately does not expose storefront commands such as customer review
submission, helpful voting, abuse reporting, or guest question subscription.
Admin mutations cover configuration, imports, content editing, moderation,
review requests, and external synchronization.

## Database-to-API boundaries

The physical `content_item` table is an implementation detail shared by four
API aggregates:

| Database aggregate | Admin GraphQL entity | Mutation ownership |
| --- | --- | --- |
| `content_item` + `review` | `Review` | `reviewCreate/update/delete` |
| `content_item` + `review_reply` | `ReviewReply` | `reviewReplyCreate/update/delete` |
| `content_item` + `product_question` | `ProductQuestion` | `productQuestionCreate/update/delete` |
| `content_item` + `question_answer` | `ProductQuestionAnswer` | `productQuestionAnswerCreate/update/delete` |
| `store_configuration` | `ReviewStoreConfiguration` | `storeConfigurationUpdate` |
| `rating_criterion` aggregate | `ReviewRatingCriterion` | criterion create/update/delete |
| `review_request` + events | `ReviewRequest` | request create/update; events are read-only |
| reports and moderation cases | `ReviewContentReport`, `ReviewModerationCase` | first-class admin updates |
| revisions, moderation events/signals | audit node types | read-only |
| product summary tables | summary types | read-only projections |

Translations, publications, media, criterion assignments, and detailed rating
values are visible entities where they have their own lifecycle, but aggregate
sync remains available from the owning content/criterion update.

## Relay queries

Operational lists use Relay connections with `edges`, `pageInfo`, and
`totalCount`. Their arguments follow the Catalog contract:

```graphql
reviews(
  first: Int
  after: String
  last: Int
  before: String
  where: ReviewWhereInput
  orderBy: [ReviewOrderByInput!]
  meta: ReviewContentConnectionMetaInput
): ReviewConnection!
```

The `where` contract uses the same recursive `_and`, `_or`, `_not` structure and
base scalar operators generated by `@shopana/drizzle-query`. Order enums use
field names from the planned flat admin list read models and the shared
lower-case `SortDirection` values.

Repository implementations must follow the Catalog pattern:

- build a flat list read model for every connection;
- create `createRelayQuery(createQuery(view).include(["id"])...)`;
- use `{ name: "<entity>", tieBreaker: "id" }`;
- default to 20 and cap at 100;
- inject `storeId` and soft-delete scope in the repository, never from client
  input;
- map every ID filter from Relay global ID to the database UUID;
- default to `createdAt desc, id desc`, or the queue-specific indexed order;
- execute the page and `count()` with the same merged `where` input.

The current Reviews service has migrations but no Drizzle table/read-model
definitions yet. Therefore `filters.graphql` is the SDL design source for this
step. When repositories are implemented, the same public fields should move to
`generateWhereInputType` and `generateOrderByInputType` without changing the
GraphQL contract.

## Unified update contract

First-class updates mirror Catalog `productUpdate`:

```graphql
reviewUpdate(
  reviewId: ID!
  expectedRevision: Int!
  operations: ReviewUpdateInput
): ReviewUpdatePayload!
```

The identity and optimistic-lock token are mutation arguments. `operations` is
section-based, omitted sections are no-ops, explicit `null` clears nullable
fields, and collection sections document full replacement semantics. Every
update returns the updated entity, ordered `operationResults`, and flattened
`userErrors`.

Entities backed by a database `revision` use `expectedRevision`. Other mutable
first-class rows use `expectedUpdatedAt`, matching their existing physical
concurrency token without inventing a schema column.

## Federation and IDs

Reviews owns global IDs for its first-class nodes. Product, Variant, Category,
Customer, and File are federation references only; their existence and tenant
scope must be validated through service contracts rather than cross-schema SQL
joins. Order and order-line evidence remains exposed as IDs until Orders owns
resolvable admin federation entities.
