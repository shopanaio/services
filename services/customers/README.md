# Customers Service

Customers Service — ограниченный контекст для управления покупателями внутри конкретного Store.
Сервис хранит бизнес-профиль покупателя, адреса, налоговые данные, маркетинговые согласия,
классификацию и агрегированную статистику.

## Границы ответственности

Customers не является сервисом аутентификации. Учетные данные, пароли, сессии, токены подтверждения
и идентичность для входа принадлежат IAM. Поле `customer.iam_principal_id` только связывает
бизнес-профиль покупателя с principal в IAM и может быть `NULL` для гостя или импортированного
клиента.

Orders остается источником истины для заказов, Payments — для платежей и денежного реестра, Media —
для файлов. Customers хранит только ссылки на сущности этих сервисов без межсервисных внешних
ключей.

Customers также владеет единым сохранённым набором вариантов товаров для сравнения
аутентифицированного покупателя. В нём хранятся упорядоченные пары Catalog `product_id` +
`variant_id`; Catalog динамически группирует их по текущей primary category. Один Product может
занимать несколько колонок, если выбраны разные variants. Storefront не получает persistence-модель
Customers: Catalog расширяет `Customer` через federation полем `productComparisons` и возвращает
category-based presentation-ready матрицы без знания о профилях, нормализации, единицах измерения и
правилах сравнения. Гостевой набор сравнения хранится storefront-клиентом и не создаёт Customer
данные.

Customers хранит приватные списки желаний аутентифицированного покупателя. Каждый список имеет
уникальное для Customer нормализованное имя, один из существующих списков назначается стандартным, а
элементы содержат только межсервисные ссылки на Catalog Product. Публикация и storefront-доступность
Product проверяются через Catalog и не дублируются в Customers.

Все данные привязаны к магазину: каждая таблица содержит `store_id`, а репозитории обязаны получать
Store из доверенного контекста запроса.

### Checkout eligibility

Customers публикует read-only broker action `customers.resolveCheckoutBuyerEligibility`. Он
разрешает только существующего Customer из доверенного Store context, применяет lifecycle policy и
возвращает неизменяемый snapshot активных сегментов на переданный `effectiveAt`.

Checkout разрешен только для lifecycle `ACTIVE`. Удаленный Customer и Customer другого Store не
раскрываются, а `DISABLED`, `BLOCKED`, `MERGED` и `REDACTED` возвращаются как non-retryable business
failures без внутренних причин, merge target или PII. Customers не создает и не изменяет профиль
через этот action и не выполняет dynamic rules синхронно.

Membership действует при `evaluated_at <= effectiveAt` и отсутствующем `expires_at` либо
`expires_at > effectiveAt`. RULE membership дополнительно должен быть вычислен по текущему
`definition_revision` сегмента. Segment IDs уникальны, отсортированы, ограничены 500 значениями и
сопровождаются стабильной SHA-256 revision исходных membership rows.

## Сущности

### Профиль покупателя

| Сущность   | Назначение                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `customer` | Основная бизнес-сущность покупателя. Хранит имя, контактные проекции, дату рождения, язык, компанию, заметку продавца, заметку модератора, причину текущего отключения, источник создания и состояние жизненного цикла. Поддерживает гостевые, приглашенные и зарегистрированные профили, блокировку, обезличивание и ссылку на результат объединения. Email и состояние подтверждения здесь являются проекцией; идентичность для входа остается в IAM. |

`customer.lifecycle_status` описывает состояние бизнес-профиля:

- `active` — профиль доступен для обычных операций;
- `disabled` — профиль отключен, но не помечен как рискованный;
- `blocked` — операции покупателя заблокированы магазином; непустая причина блокировки обязательна;
- `merged` — профиль объединен с другим Customer;
- `redacted` — персональные данные обезличены процессом конфиденциальности.

`customer.account_status` отделен от жизненного цикла:

- `guest` — профиль не связан с учетной записью IAM;
- `invited` — покупателю предложено создать или активировать учетную запись;
- `registered` — профиль связан с зарегистрированным principal.

IAM является источником истины для `email`, `email_verified`, `first_name`, `last_name` и состояния
application user. IAM block переводит только `ACTIVE` Customer в `DISABLED` и помечает, что переход
выполнен IAM; он не создает merchant-risk состояние `BLOCKED`. IAM unblock возвращает `ACTIVE`
только при наличии этой метки. Удаление application user отвязывает `iam_principal_id`, сбрасывает
IAM-owned verification и переводит `REGISTERED` в `GUEST`, не отменяя независимо установленный
merchant lifecycle.

### Адреса

| Сущность           | Назначение                                                                                                                                                                                                                                                                         |
| ------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `customer_address` | Многоразовый почтовый адрес покупателя: получатель, компания, телефон, две строки адреса, город, регион, индекс и страна. Один адрес может быть стандартным адресом доставки, стандартным платежным адресом или обоими. Также хранит результат проверки и опциональные координаты. |

У Customer может быть любое количество адресов, но частичные уникальные индексы разрешают не более
одного активного стандартного адреса доставки и одного стандартного платежного адреса.

### Списки желаний

| Сущность                 | Назначение                                                                                                                                                          |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `customer_wishlist`      | Именованный приватный список товаров Customer. Хранит отображаемое и нормализованное имя, признак стандартного списка и временные метки для optimistic concurrency. |
| `customer_wishlist_item` | Сохранённая ссылка на Catalog Product. Один Product может присутствовать в каждом списке не более одного раза.                                                      |

Если у Customer существуют списки желаний, один из них назначается стандартным. База данных
запрещает несколько стандартных списков и повтор Product внутри одного списка; создание первого
стандартного списка и запрет его удаления обеспечиваются транзакционным workflow.

### Налоговые данные

| Сущность                  | Назначение                                                                                                                                                                                         |
| ------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `customer_tax_identifier` | Налоговые номера покупателя или компании, например VAT ID. Хранит тип, страну, исходное и нормализованное значение, статус проверки и период действия. Один идентификатор можно отметить основным. |
| `customer_tax_exemption`  | Налоговые льготы и освобождения. Хранит код освобождения, юрисдикцию, причину, статус, срок действия и ссылку на подтверждающий файл в Media.                                                      |

Налоговые идентификаторы и освобождения разделены: наличие налогового номера само по себе не
означает освобождения Customer от налога.

### Маркетинговые согласия

| Сущность                 | Назначение                                                                                                                                                                                                                       |
| ------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `customer_consent`       | Текущее состояние согласия по одному каналу: email, SMS, WhatsApp или push. Хранит контакт, состояние подписки, уровень согласия, источник, время предоставления и время отзыва.                                                 |
| `customer_consent_event` | История изменений согласия. Фиксирует предыдущее и новое состояние, источник, автора действия, ключи запроса и идемпотентности, а также подтверждающие данные. Используется для аудита того, где и когда было получено согласие. |

Согласие не хранится одним логическим значением. Состояния `pending`, `subscribed`, `unsubscribed`,
`invalid` и `redacted` позволяют корректно обрабатывать двойное подтверждение подписки, отзыв
согласия и удаление персональных данных.

### Группы, теги и сегменты

| Сущность                      | Назначение                                                                                                                                                                                                                                                                                               |
| ----------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `customer_group`              | Управляемая магазином бизнес-группа, например `retail`, `wholesale` или `vip`. Может использоваться политиками ценообразования, налогообложения и продвижения. Store может иметь одну стандартную группу и revision агрегата для оптимистической блокировки определения, состояния и состава участников. |
| `customer_group_membership`   | Связь Customer с группой. Хранит признак основной группы, источник назначения, автора и срок действия. Модель допускает несколько групп, но только одну активную основную группу.                                                                                                                        |
| `customer_tag`                | Свободная метка продавца, например `influencer`, `fraud-review` или `newsletter-2026`. Имеет нормализованное уникальное имя внутри Store.                                                                                                                                                                |
| `customer_tag_assignment`     | Связь Customer с тегом и информация о том, кто и когда назначил тег.                                                                                                                                                                                                                                     |
| `customer_segment`            | Сохраненная аудитория покупателей. Ручной сегмент заполняется явно, динамический содержит запрос или JSON-правило вычисления участников. Может иметь выбранный продавцом цвет и revision агрегата для оптимистической блокировки определения и состава участников.                                       |
| `customer_segment_membership` | Материализованное участие Customer в сегменте. Хранит источник вычисления, время оценки и опциональный срок действия.                                                                                                                                                                                    |

Эти понятия не взаимозаменяемы:

- группа — стабильная бизнес-классификация, способная влиять на правила магазина;
- тег — простая ручная метка без собственной бизнес-логики;
- сегмент — аудитория для поиска, аналитики, продвижения и маркетинговых кампаний.

### Интеграции

| Сущность                      | Назначение                                                                                                                                                                                 |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `customer_external_reference` | Связывает Customer с идентификатором во внешней CRM, ERP, маркетплейсе или устаревшей системе. Используется для идемпотентного импорта и обновления, предотвращая дубли при синхронизации. |

### Статистика

| Сущность                                                                                  | Назначение                                                                                                                                                                                     |
| ----------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `customer_statistics`                                                                     | Восстанавливаемая модель чтения со счетчиками заказов и возвратов, первым и последним заказом, а также последним Checkout. Источником истины остаются Orders и Checkout.                       |
| `customer_monetary_statistics`                                                            | Восстанавливаемая модель чтения с количеством заказов, потраченной, возвращенной и итоговой суммой, а также средним чеком отдельно по каждой валюте. Денежные значения хранятся в minor units. |
| `customer_order_projection`, `customer_checkout_projection`, `customer_refund_projection` | Идемпотентные revision-aware факты, из которых Customers пересобирает статистику после событий Orders, Checkout и Refund/Payments.                                                             |

Статистика предназначена для списка покупателей, сортировки, RFM-сегментации и маркетинговых правил.
Ее можно пересобрать из событий других ограниченных контекстов.

Изменение профиля или статистики fail-closed удаляет устаревшие RULE memberships. Полноценная
пересборка динамических сегментов появится вместе с каноническим DSL/materializer; текущий
administrative action явно возвращает число invalidated memberships и не имитирует вычисление
правил.

### Жизненный цикл и конфиденциальность

| Сущность                | Назначение                                                                                                                                                                                                           |
| ----------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `customer_merge`        | Идемпотентный процесс объединения дубликатов. Хранит исходного и целевого Customer, статус, инициатора, решение, ошибки и временные метки. После успешного объединения исходный профиль получает состояние `merged`. |
| `customer_data_request` | Процесс обработки запросов на доступ, экспорт, исправление и удаление персональных данных. Хранит статус, заявителя, правовое основание, срок исполнения, результат в Media и причину отклонения.                    |

Объединение и удаление данных представлены отдельными сущностями процессов, чтобы операции можно
было безопасно повторять, отслеживать и аудитировать.

## Основные инварианты

- Активный нормализованный email уникален внутри Store.
- Один principal IAM связан максимум с одним Customer внутри Store.
- Гостевой Customer может существовать без principal IAM.
- Customer не может быть объединен сам с собой.
- Заблокированный Customer всегда имеет причину; у остальных состояний жизненного цикла причины
  блокировки нет.
- Один адрес может одновременно быть стандартным для доставки и оплаты.
- Состояние согласия должно соответствовать времени предоставления и отзыва.
- Денежная статистика не допускает отрицательных сумм и сохраняет `net = spent - refunded`.
- UUID-идентификаторы генерируются PostgreSQL-функцией `uuidv7()`.
- Revision группы изменяется при обновлении определения, состояния и ручного состава участников.
- Aggregate revision сегмента изменяется при принятом обновлении определения, состояния или состава
  участников. Отдельный `definition_revision` изменяется только при изменении type, query или
  структурного JSON definition.
- RULE membership хранит `evaluated_definition_revision`; остальные источники обязаны хранить
  `NULL`.

## Контракт обновления Admin

`customerUpdate` принимает один `customerId`, обязательный `expectedRevision` и набор секций. Помимо
профиля, контактов, компании, состояния, заметки и модерации, операция поддерживает адреса, переходы
согласий, налоговые идентификаторы, налоговые освобождения, участие в группах, назначения тегов и
ручное участие в сегментах.

Вложенные входные данные не содержат `customerId`: все идентификаторы проверяются как принадлежащие
обновляемому Customer и текущему Store.

Секции назначений используют семантику полной замены. Пустые `tagIds`, `segmentIds` или
`memberships` очищают соответствующие ручные связи. Отсутствующая секция не изменяет данные.

`customerSegmentUpdate` аналогично может изменить сведения, определение и состояние, а также
заменить ручной состав покупателей при одном обязательном `expectedRevision`. Изменение только
состава выполняется через `customerSegmentUpdate.operations.memberships.setCustomerIds`.

`customerGroupUpdate` изменяет определение, состояние и состав участников при одном обязательном
`expectedRevision`.

`store_id` не входит в первичные и внешние ключи; tenant isolation обеспечивается обязательным
ограничением запросов по Store и отдельными индексами.

## Структура миграций

Миграции находятся в `migrations/domains/**/*.sql` и выполняются через `node-pg-migrate` в режиме
glob. Порядок доменов:

1. схема и enum-типы;
2. профили;
3. адреса;
4. налоговые данные;
5. маркетинговые согласия;
6. классификация;
7. preferences, включая persisted comparison и wishlists;
8. интеграции;
9. статистические модели чтения;
10. жизненный цикл и конфиденциальность.

Модели Drizzle времени выполнения находятся в `src/repositories/models/` и повторяют контракт
написанных вручную SQL-миграций.

Подробные технические решения и ограничения описаны в
[docs/customers-database-schema.md](docs/customers-database-schema.md).

## Инфраструктура сервиса

Customers использует те же инфраструктурные соглашения, что Catalog и Listing:

- модуль NestJS и интеграцию с bootstrap;
- написанные вручную миграции PostgreSQL через `node-pg-migrate`;
- схему Drizzle времени выполнения и агрегатор репозиториев с поддержкой транзакций;
- контекст запроса, kernel, загрузчики и точки входа сценариев;
- Admin GraphQL server на основе классов, пространства имен resolver и codegen.
